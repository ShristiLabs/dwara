How to use Dwara Config Studio

    
The workflow

    
    
      
  1. Pick a template (or start blank) and edit through the forms in the middle. Required fields are open; optional fields are collapsed under "optional fields".
    2. 
      
  2. Check the YAML pane on the right - it is the actual config, always in sync. You can also paste an existing config there and "Apply to builder" to edit it as forms.
    3. 
      
  3. Validate - the status bar is always live. Green means structurally valid; click it for details, and click an issue to jump to the field.
    4. 
      
  4. Download dwara.yaml, then load it into Dwara separately: dwara validate dwara.yaml and DWARA_CONFIG=dwara.yaml dwara run. Browser checks are structural only; dwara validate is the final word.
    5. 
    

    
How a config fits together

    
A request flows listener → route → service → upstream → endpoints: a listener binds a port (with optional TLS), a route matches a path and points at a named service, the service names the upstream (its load-balancing pool), and the pool lists endpoint addresses. Names are cross-references - the Overview wiring table shows the chains and flags any dangling name in red. Consumers hold credentials (API key, JWT, mTLS, HMAC) and can carry policies (rate limits, timeouts, budgets) that attach by name at any level.

    
Good to know

    
    
      
  • Secrets - write ${NAME} or ${file:/path} references instead of real values; this tool never resolves them.
    • 
      
  • Drafts autosave to this browser (localStorage). Clear wipes the draft.
    • 
      
  • Cross-reference fields (service, upstream, policies) are dropdowns/chips fed by the entities you have defined.
    • 
      
  • Feature-gated blocks (mesh, plugins, h3 upstreams...) are accepted in config but inert unless Dwara is built with the matching cargo feature - validation notes this where relevant.
