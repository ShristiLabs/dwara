1//! Gateway core: the shared config model, routing types, swappable trait
2//! definitions, listener/TLS machinery, and dataplane assembly consumed by
3//! the bin/admin/cli crates.
4//!
5//! # Organization
6//!
7//! This crate is organized as a set of domain directories (bounded
8//! contexts) behind this facade:
9//!
10//! - [`config`] — configuration schema and the `parse_gateway` entry point
11//! - [`extensions`] — the OSS/Ent edition boundary as a type boundary
12//! - [`snapshot`] — the config compile pipeline (validate -> compile -> publish)
13//! - [`observability`] — tracing, metrics, and access logging
14//! - [`events`] — the in-process event bus and webhook delivery (DW-044)
15//! - [`state`] — SQLite-backed durable state and schema migrations
16//! - [`security`] — TLS, authentication, authorization
17//! - [`resilience`] — passive health, retries, circuit breaker,
18//!   adaptive + origin-driven rate-limit tuning (DW-089)
19//! - [`dataplane`] — the reverse-proxy request path, its upstreams, and
20//!   active health probing
21//! - [`supervision`] — bounded panic-respawn supervision for accept
22//!   loops, shared by the bin and admin accept surfaces
23//! - [`error`] — the facade-level aggregate [`error::Error`] over the
24//!   domain error types, for boundary propagation
25//!
26//! # Dependency direction
27//!
28//! Dependencies point downward only; a domain may never be depended on by
29//! a domain above it:
30//!
31//! | Domain | May depend on |
32//! |---|---|
33//! | `config` | (nothing) |
34//! | `extensions` | `config` |
35//! | `observability` | (nothing) |
36//! | `events` | `config`, `observability` |
37//! | `snapshot` | `config`, `events` |
38//! | `state` | `config` |
39//! | `analytics` | `config`, `observability`, `extensions` |
40//! | `security` | `config`, `state`, `observability` |
41//! | `resilience` | `config`, `snapshot`, `extensions`, `observability`, `events` |
42//! | `plugins` | `config` (native filter trait + unified dispatch chain;
43//!   the `wasm` domain bridges its instances in via a generic adapter,
44//!   so `plugins` never imports `wasm` — see DW-119) |
45//! | `ai` | `config` (provider-adapter pack, DW-075: the canonical chat
46//!   vocabulary, the pure-translation [`ai::adapter::ProviderAdapter`]
47//!   seam, and the compiled alias table; the transport lives in
48//!   `dataplane`, which calls into it) |
49//! | `lifecycle` | `config`, `observability`, `analytics` (DW-110: API
50//!   lifecycle management -- developer portal, environment profiles,
51//!   API journey recorder; feature-gated behind `api_lifecycle`) |
52//! | `mesh` | `config`, `observability` (DW-107: service mesh mode --
53//!   sidecar traffic interception + SPIFFE/SPIRE mTLS identity; the
54//!   mTLS TLS integration point is a documented seam into `security`,
55//!   kept as a hand-off so the dependency direction stays downward;
56//!   feature-gated behind `mesh`, Ent-only) |
57//! | `dataplane` | all of the above |
58//! | `supervision` | (nothing — pure task plumbing, no domain imports) |
59//!
60//! (`dwara-bin`, `dwara-admin`, and `dwara-cli` depend on this crate.)
61//!
62//! # Path compatibility
63//!
64//! The modules were originally flat at the crate root. To keep every
65//! pre-restructure path (e.g. `dwara_core::proxy::handle`,
66//! `dwara_core::config::parse_gateway`, `dwara_core::tls`) compiling
67//! unchanged, the crate root re-exports each moved module as a path alias:
68//! `dwara_core::proxy` and `dwara_core::dataplane::proxy` (and likewise
69//! for `upstream`, `balance`, `hardening`, `health`, `active`, `retries`,
70//! `breaker`, `tls`, `authn`, `authz`, `store`, `migrations`) denote the
71//! same module. The aliases are `#[doc(hidden)]`: they still compile but
72//! stay out of the rendered docs. Use the domain-qualified path in new
73//! code (`dwara_core::dataplane::proxy`, `dwara_core::security::tls`).
