# Category 07: AI Gateway

Demonstrates dwara's AI gateway capabilities using the default OSS build:
provider adapters, model aliasing, failover, canary splits, pricing,
token budgets, model governance, guardrails, prompt logging, streaming,
and the MCP gateway.

## What it covers

- **Provider adapters** — OpenAI and Anthropic wire-protocol adapters
  (DW-075) translating a canonical chat request to each provider's shape
- **Model aliasing** — the `model` field in a client request maps to a
  provider + provider model
- **Failover chains** — primary returns 429/5xx, the gateway falls over
  to the next provider in the chain
- **Weighted canary** — split traffic across model versions (90/10)
- **Per-model pricing** — micro-USD per 1K tokens (DW-079)
- **Token budgets** — per-consumer and per-policy tokens-per-minute /
  cost-per-day caps (DW-078)
- **Model governance** — per-team model allowlists, deny at the edge
  with 403 before routing (DW-084)
- **Guardrails** — prompt-injection block + PII redaction (DW-082)
- **Prompt logging** — opt-in capture with redaction (DW-081), queried
  via the mTLS admin API
- **MCP gateway** — JSON-RPC tools/list over `/mcp` (DW-087)
- **Streaming SSE** — Server-Sent Events re-framing for `stream: true`

## Architecture

```
                       +-----------+
  HTTP :8080 --------->|           |
                       |  dwara    |----> ai-mock:8080    (openai adapter)
  Admin :2019 (mTLS)-->| gateway   |----> ai-mock-2:8080  (anthropic adapter)
                       +-----------+
```

- **edge-http** (0.0.0.0:8080) — plaintext HTTP entry point for all
  chat-completions and MCP tests
- **admin** (0.0.0.0:2019) — mTLS-only admin API (prompt-logs query)
- **ai-mock** — OpenAI-compatible mock provider (the `openai` adapter
  upstream); returns canned responses by model name, 429 for
  `rate-limit-test`, 500 for `error-test`, SSE for `stream: true`
- **ai-mock-2** — second OpenAI-compatible mock provider (the
  `anthropic` adapter upstream); the failover and canary target

## Prerequisites

The shared infrastructure must be built first:

```sh
# Build the mock AI provider image (from the repo root).
docker build -t dwara-demo/ai-mock demos/_shared/upstreams/ai-mock/

# Build the gateway image (from the repo root).
docker build -f Dockerfile.scratch -t dwara:demo .

# Ensure certs exist (generated by quickstart/gen-certs.sh).
ls demos/_shared/certs/server.crt demos/_shared/certs/client-ca.crt
```

## Running

```sh
# Start the gateway + both mock AI providers.
docker compose up -d

# Wait for the gateway to be ready, then run tests:
./test-01-provider-adapters.sh
./test-02-model-alias.sh
./test-03-failover-chain.sh
./test-04-model-canary.sh
./test-07-guardrails.sh
./test-08-prompt-logging.sh
./test-11-mcp-gateway.sh
./test-13-model-governance.sh
./test-14-streaming-sse.sh

# Tear down.
docker compose down -v
```

## Configuration

See `dwara.yaml` for the full gateway config. Key sections:

- **Upstreams** — `ai-primary` (ai-mock:8080) and `ai-secondary`
  (ai-mock-2:8080), both HTTP/1
- **Analytics** — SQLite analytics store at `/var/lib/dwara/analytics.db`
  (required for prompt logging)
- **Providers** — `openai` (upstream ai-primary) and `anthropic`
  (upstream ai-secondary)
- **Models** — `gpt-4o-mini` (simple), `gpt-4o` (failover to anthropic),
  `gpt-4o-canary` (90/10 canary split), `rate-limit-test` (failover
  under 429)
- **Consumer** — `demo-user` (API key `demo-ai-key`) with a per-consumer
  token budget and prompt logging opted in
- **Policy** — `ai-budget` with a policy-level token budget and a team
  allowlist (`gpt-4o-mini`, `gpt-4o`, `gpt-4o-canary`, `rate-limit-test`)
- **Guardrails** — `block-injection` (block) and `redact-pii` (redact)
- **MCP** — `/mcp` with `search_docs` and `get_status` tools

## Authentication

All chat-completions tests authenticate with the `demo-user` consumer's
API key:

```sh
curl -X POST \
  -H 'X-API-Key: demo-ai-key' \
  -H 'Content-Type: application/json' \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Hello"}]}' \
  http://localhost:8080/v1/chat/completions
```

## Certificates

Certificates are shared across all demos at `demos/_shared/certs/`. The
prompt-logging test (`test-08`) queries the mTLS-only admin API using the
client certificate. The admin API presents a self-signed server cert
(CN=localhost), so the server certificate is used as the trusted CA:

```sh
curl --cacert ../_shared/certs/server.crt \
     --cert ../_shared/certs/client.crt \
     --key ../_shared/certs/client.key \
     -X POST -H 'Content-Type: application/json' \
     -d '{"from_ms": 0, "to_ms": 9999999999999, "consumer": "demo-user"}' \
     https://localhost:2019/analytics/prompt-logs
```

## Networking

The mock providers are pinned to static IPs on a dedicated bridge network
(`ai-net`, subnet `172.28.0.0/16`). The gateway's `/etc/hosts` is seeded
with the provider names and their static IPs via Docker `extra_hosts` so
the gateway's async DNS resolver (hickory) resolves them from the hosts
file without a network round-trip. This avoids the Docker embedded DNS
resolver (`127.0.0.11`), which the gateway's resolver does not query by
default (it uses public resolvers `8.8.8.8`/`8.8.4.4` unless configured
otherwise).
