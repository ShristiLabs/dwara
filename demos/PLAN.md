# Dwara Demo Apps Plan

Sample/demo apps to visualize and test every dwara functionality, organized
by **Category > Feature > Functionality**. Each demo is a self-contained
directory under `demos/` with its own `dwara.yaml`, `docker-compose.yml`,
a test upstream (when needed), and a `test.sh` that exercises the feature
with `curl` and asserts the expected behavior.

## Design principles

1. **Shared infrastructure.** All demos reuse the existing `quickstart/certs/`
   (generated by `quickstart/gen-certs.sh`) and a shared set of upstream
   images. A single `demos/_shared/` directory holds common upstream
   services, helper scripts, and the cert-generation wrapper.
2. **One compose per category.** Each category gets one `docker-compose.yml`
   that starts the gateway + all upstreams needed for that category's demos.
   Individual `test-*.sh` scripts exercise specific features. This avoids
   rebuilding the gateway image for every demo.
3. **Minimal upstreams.** Most demos use `nginx:alpine` (static files),
   `httpbin` (echo/inspect), or a tiny Python `http.server` script for
   dynamic behavior. No heavy upstream frameworks.
4. **OSS-first.** Every demo targets the default OSS build unless explicitly
   marked **[Ent]** (enterprise) or **[Pack:\<flag\>]** (cargo feature).
5. **Reusable demo apps.** The same upstream images are reused across
   categories. A "flaky upstream" (random 500s), a "slow upstream"
   (configurable delay), and an "echo upstream" (reflects request) are built
   once and referenced everywhere.

## Category 1: Core Gateway & Routing

### Shared upstreams
- `static` (nginx:alpine) — serves `index.html`, `/api/users.json`,
  `/api/products.json`, `/healthz`
- `echo` (Python) — reflects method, path, headers, body as JSON

### Demos

#### 1.1 Routing & Match Types

| Demo | Functionality | How to test | Expected |
|---|---|---|---|
| **test-01-exact-match** | Route matches `exact: /healthz` and responds directly | `curl http://localhost:8080/healthz` | 200 `ok` |
| **test-02-prefix-match** | Route matches `prefix: /v1/` and proxies with `strip_prefix` | `curl http://localhost:8080/v1/api/users.json` | 200 JSON from upstream `/api/users.json` |
| **test-03-regex-match** | Route matches `regex: /v1/users/[^/]+` | `curl http://localhost:8080/v1/users/42` | 200 from upstream |
| **test-04-redirect** | `redirect` action with 301 | `curl -I http://localhost:8080/users` | 301 to `https://localhost/v1/users` |
| **test-05-respond-direct** | `respond` action with fixed body | `curl http://localhost:8080/healthz` | 200 `ok` with `Content-Type: text/plain` |
| **test-06-mock-response** | `mock` action with delay | `curl -w '%{time_total}' http://localhost:8080/v1/mock` | 200 `{"mock": true}` with ~50ms delay |
| **test-07-path-rewrite** | `strip_prefix` rewrite | `curl http://localhost:8080/v1/api/users.json` | upstream receives `/api/users.json` (verified via echo upstream) |
| **test-08-method-allowlist** | Method not in allowlist returns 405 | `curl -X PATCH http://localhost:8080/v1/` | 405 + `Allow` header |
| **test-09-api-versioning** | Path-based versioning + deprecation headers | `curl -I http://localhost:8080/v1/` | `Deprecation` + `Sunset` headers present |
| **test-10-host-header-match** | Route matches by `host` header | `curl -H 'Host: api.example.com' http://localhost:8080/` | routed to correct upstream |

| Demo | Functionality | How to test |
|---|---|---|
| **test-11-grpc-websockets** | gRPC + WebSocket proxying on same listener | `grpcurl` + `websocat` against the gateway |

## Category 2: Load Balancing & Upstream Management

### Shared upstreams
- 3x `echo` instances (echo-a, echo-b, echo-c) — each returns its hostname
- `slow` — configurable delay per path (`/slow/500` = 500ms)
- `flaky` — returns 500 on configurable % of requests (`/flaky/50` = 50% errors)

### Demos

| Demo | Functionality | How to test | Expected |
|---|---|---|---|
| **test-01-round-robin** | `load_balancer: round_robin` distributes evenly | 10x `curl http://localhost:8080/lb/` | ~33% to each echo instance |
| **test-02-least-requests** | `load_balancer: least_requests` sends to least-busy | concurrent requests against slow upstream | requests pile on different endpoints |
| **test-03-ip-hash** | `load_balancer: ip_hash` — same client always hits same endpoint | 10x `curl` from same IP | all go to same echo instance |
| **test-04-peak-ewma** | `load_balancer: peak_ewma` — latency-aware selection | mix fast + slow endpoints | traffic skews to fast endpoint |
| **test-05-sticky-sessions** | Cookie affinity | `curl -c cookies.txt ...` then `curl -b cookies.txt ...` | same backend each time |
| **test-06-traffic-split** | Weighted split 90/10 | 100x `curl http://localhost:8080/canary/` | ~90 to stable, ~10 to canary |
| **test-07-dns-discovery** | DNS-based dynamic endpoint discovery | `dig` + check gateway logs for DNS refresh | endpoints refresh from DNS |
| **test-08-slow-start** | New endpoint ramps up gradually | add endpoint, observe traffic ramp | traffic to new endpoint increases over `slow_start_ms` |
| **test-09-happy-eyeballs** | RFC 8305 dual-stack connection racing | dual-stack endpoint (IPv4 + IPv6) | connects via faster stack |

## Category 3: Traffic Policy & Resilience

### Shared upstreams
- `flaky` — configurable error rate
- `slow` — configurable latency
- `echo` — healthy baseline

### Demos

| Demo | Functionality | How to test | Expected |
|---|---|---|---|
| **test-01-passive-health** | Endpoint ejected after `consecutive_failures` | send 5 failing requests to flaky upstream | endpoint ejected, subsequent requests go to healthy endpoint |
| **test-02-active-health** | Active HTTP probes detect unhealthy endpoint | stop one echo container, wait `interval_ms` | gateway marks it unhealthy, routes to others |
| **test-03-circuit-breaker** | Breaker opens after error threshold | flood flaky upstream | breaker opens, returns 502/503; after `open_ms` half-open probe |
| **test-04-retries** | Retry on 502/503 with backoff | `curl` to flaky upstream with 50% error rate | request eventually succeeds (retries kick in) |
| **test-05-hedging** | Speculative retry after `hedge_after_ms` | `curl` to slow upstream (300ms response) | response arrives in ~200ms (hedge wins) |
| **test-06-timeouts** | Connect/read/write timeouts | `curl` to slow upstream exceeding `read_ms` | 504 Gateway Timeout |
| **test-07-connection-cap** | `connection_cap` limits outbound connections | flood with concurrent requests beyond cap | excess requests get 502 or queue |
| **test-08-load-shedding** | `max_concurrent_requests` sheds excess | flood gateway beyond cap | excess requests get 503 |
| **test-09-admission-queue** | Queued requests wait instead of shed | flood gateway, observe queue wait time | requests admitted within `queue_timeout_ms` |
| **test-10-fault-injection** | Delay + abort injection | `curl` multiple times | ~5% get 100ms delay, ~1% get 503 |
| **test-11-mirroring** | Shadow traffic to mirror upstream | send requests, check mirror upstream logs | ~10% of traffic appears on mirror |
| **test-12-maintenance-mode** | Route returns 503 + Retry-After | enable maintenance on a route | `curl` returns 503 with `Retry-After: 120` |

## Shared upstream implementations

### echo (Python http.server)
Reflects the request as JSON: method, path, query params, headers, body.
Used by routing, transforms, auth, and LB demos to verify what the gateway
sent to the upstream.

### flaky (Python)
Returns 500 on a configurable percentage of requests. Path-based control:
`/flaky/30` returns 500 for 30% of requests. Used by resilience demos
(passive health, circuit breaker, retries, hedging).

### slow (Python)
Adds a configurable delay before responding. Path-based: `/slow/500` delays
500ms. Used by timeout, hedging, and peak-EWMA demos.

### ws-echo (Python websockets)
WebSocket echo server. Used by WebSocket proxying demos.

### grpc-echo (Python grpc)
gRPC server with unary and streaming methods. Used by gRPC-Web and
gRPC proxying demos.

### ai-mock (Python)
OpenAI-compatible mock provider. Implements:
- `POST /v1/chat/completions` — returns canned responses by model name
- `POST /v1/chat/completions` with `stream: true` — SSE streaming
- `POST /v1/embeddings` — returns fixed-dimension embeddings
- Returns 429 for `rate-limit-test` model (for failover/quarantine tests)
- Returns 500 for `error-test` model (for circuit breaker tests)

### webhook-receiver (Python)
HTTP server that receives webhook events and analytics-stream batches,
prints them to stdout, and stores them in a JSON file for test assertions.
Used by observability and event demos.

## Build & run

```sh
# One-time: generate certs (reuses quickstart/gen-certs.sh)
cd demos/_shared && ./gen-certs.sh

# Build shared upstream images
docker compose -f demos/_shared/docker-compose.yml build

# Run a category (each is independent)
cd demos/01-routing
docker compose up -d
./test-01-exact-match.sh
./test-02-prefix-match.sh
# ...
docker compose down
```

Each `test-*.sh` script:
1. Waits for the gateway to be healthy (`/healthz`)
2. Sends the test request(s)
3. Asserts the expected status code / headers / body
4. Prints PASS/FAIL with a description
