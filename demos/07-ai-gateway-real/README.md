# Category 07 (real LLMs): AI Gateway

Demonstrates dwara's AI gateway capabilities against **real LLM backends**
instead of mocks. Three OpenAI-compatible providers are wired:

- **z.ai (GLM-5.3)** — cloud API, GLM Coding Plan at `https://api.z.ai/api/coding/paas/v4`
- **Ollama (llama3.2)** — local, at `http://localhost:11434/v1`
- **LM Studio** — local, at `http://localhost:1234/v1`

All three use `kind: openai` (the OpenAI chat-completions dialect). z.ai
uses a non-standard path (`/api/coding/paas/v4` for the GLM Coding Plan).
The `path` override on the zai provider replaces the OpenAI adapter's
default `/v1/chat/completions` with `/api/coding/paas/v4/chat/completions`,
so the gateway connects directly to `api.z.ai:443` over HTTPS — no
external reverse proxy (nginx) is needed.

## What it covers

- **Provider adapters** — three real OpenAI-compatible backends (z.ai,
  Ollama, LM Studio) through the `openai` adapter
- **Provider path override** — the zai provider uses `path:` to override
  the adapter's default path, bridging non-standard API endpoints without
  an external reverse proxy
- **Model aliasing** — client sends an alias; the gateway maps it to a
  provider + provider model; the provider model never leaks
- **Failover chains** — a dead primary (unreachable port) forces
  failover to ollama
- **Weighted canary** — 50/50 traffic split across zai and ollama
- **Streaming SSE** — `stream: true` re-framing for real LLM streams
- **Per-model pricing** — micro-USD per 1K tokens (DW-079)
- **Token budgets** — per-consumer and per-policy caps (DW-078)
- **Model governance** — per-team model allowlists (DW-084)
- **Guardrails** — prompt-injection block + PII redaction (DW-082)
- **Prompt logging** — opt-in capture with redaction (DW-081)

## Architecture

```
                          +-----------+
  HTTP :8080 -----------> |           |
                          |  dwara    |----> host.docker.internal:11434  (ollama, openai adapter)
  Admin :2019 (mTLS)-----> |  gateway  |----> host.docker.internal:1234   (lm studio, openai adapter)
                          |           |----> api.z.ai:443                  (z.ai, openai adapter + path override)
                          +-----------+
```

- **edge-http** (0.0.0.0:8080) — plaintext HTTP entry point
- **admin** (0.0.0.0:2019) — mTLS-only admin API (prompt-logs query)
- **z.ai** — cloud API reached directly over HTTPS (protocol: https,
  use_system_roots: true). The `path` override on the provider replaces
  the adapter's default `/v1/chat/completions` with
  `/api/coding/paas/v4/chat/completions`.
- **Ollama** — runs on the host, reached via `host.docker.internal`
- **LM Studio** — runs on the host, reached via `host.docker.internal`

## Prerequisites

### 1. z.ai API key (GLM Coding Plan)

Subscribe to the [GLM Coding Plan](https://z.ai/subscribe) at z.ai,
then create an API key in the [API key console](https://z.ai/manage-apikey/apikey-list).
The coding plan uses a dedicated endpoint (`/api/coding/paas/v4`) distinct
from the standard API (`/api/paas/v4`); see the
[quick start docs](https://docs.z.ai/devpack/quick-start).

The env var must include the `Bearer ` prefix because the gateway's
credential resolver requires `${...}` to be the entire config value
(not `Bearer ${...}`, which would be treated as a literal string):

```sh
export ZAI_API_KEY="Bearer your-zai-api-key"
```

If using docker-compose, set the env var in `docker-compose.yml`:

```yaml
environment:
  ZAI_API_KEY: 'Bearer your-zai-api-key'
```

### 2. Ollama

Install [Ollama](https://ollama.com) and pull the model:

```sh
ollama pull llama3.2
ollama serve   # if not already running as a service
```

Ollama's OpenAI-compatible endpoint is at `http://localhost:11434/v1`.

### 3. LM Studio

Install [LM Studio](https://lmstudio.ai), load a model (any GGUF model
from HuggingFace), and start the local server:

1. Open LM Studio, go to the **Developer** tab
2. Load a model (e.g. `meta-llama/Llama-3.2-3B-Instruct` or any model you
   have downloaded)
3. Click **Start Server** (default port `1234`)

LM Studio's OpenAI-compatible endpoint is at `http://localhost:1234/v1`.
The `provider_model` in `dwara.yaml` is set to `loaded-model`; when a
single model is loaded, LM Studio accepts any model name in the request
and uses the loaded model. Adjust the `provider_model` field to match
your loaded model's identifier if you want exact matching.

### 4. Build images and certs

```sh
# Build the gateway image (from the repo root).
docker build -f Dockerfile.scratch -t dwara:demo .

# Ensure certs exist (generated by quickstart/gen-certs.sh).
ls demos/_shared/certs/server.crt demos/_shared/certs/client-ca.crt
```

## Running

```sh
# Start the gateway.
docker compose up -d

# Wait for the gateway to be ready, then run tests:
./test-01-provider-adapters.sh
./test-02-model-alias.sh
./test-03-failover-chain.sh
./test-04-model-canary.sh
./test-05-streaming-sse.sh

# Tear down.
docker compose down -v
```

## Configuration

See `dwara.yaml` for the full gateway config. Key sections:

- **Upstreams** — `zai-upstream` (api.z.ai:443, HTTPS), `ollama-upstream`
  (host.docker.internal:11434), `lmstudio-upstream`
  (host.docker.internal:1234), `dead-upstream`
  (host.docker.internal:9999, for failover demo)
- **Providers** — `zai` (openai, path override, auth via `${ZAI_API_KEY}`),
  `ollama` (openai, no auth), `lmstudio` (openai, no auth), `dead`
  (openai, dead port)
- **Models** — `glm-5.3` (zai), `llama3.2` (ollama), `lmstudio-model`
  (lmstudio), `failover-chat` (dead -> ollama), `canary-chat`
  (50/50 zai/ollama)
- **Consumer** — `demo-user` (API key `demo-ai-key`) with a per-consumer
  token budget and prompt logging opted in
- **Policy** — `ai-budget` with a policy-level token budget and a team
  allowlist (all model aliases)
- **Guardrails** — `block-injection` (block) and `redact-pii` (redact)

### Provider path override

The zai provider uses the `path` field to override the OpenAI adapter's
default path (`/v1/chat/completions`) with the GLM Coding Plan endpoint:

```yaml
ai:
  providers:
    - name: zai
      kind: openai
      upstream: zai-upstream
      path: /api/coding/paas/v4/chat/completions
      auth:
        header: Authorization
        value: "${ZAI_API_KEY}"
```

When `path` is unset, the adapter's per-kind default path is used. This
feature bridges any provider whose API path differs from the adapter's
default without requiring an external reverse proxy.

## Authentication

All chat-completions tests authenticate with the `demo-user` consumer's
API key:

```sh
curl -X POST \
  -H 'X-API-Key: demo-ai-key' \
  -H 'Content-Type: application/json' \
  -d '{"model":"glm-5.3","messages":[{"role":"user","content":"Hello"}]}' \
  http://localhost:8080/v1/chat/completions
```

## Certificates

Certificates are shared across all demos at `demos/_shared/certs/`. The
prompt-logging test queries the mTLS-only admin API using the client
certificate:

```sh
curl --cacert ../_shared/certs/server.crt \
     --cert ../_shared/certs/client.crt \
     --key ../_shared/certs/client.key \
     -X POST -H 'Content-Type: application/json' \
     -d '{"from_ms": 0, "to_ms": 9999999999999, "consumer": "demo-user"}' \
     https://localhost:2019/analytics/prompt-logs
```

## Networking

The gateway runs on a dedicated bridge network (`ai-real-net`, subnet
`172.29.0.0/16`). `host.docker.internal` is seeded via `extra_hosts`
(using Docker's `host-gateway` keyword) so the gateway can reach Ollama
and LM Studio on the host. Docker Desktop for macOS adds
`host.docker.internal` to `/etc/hosts` automatically, but the explicit
`extra_hosts` entry guarantees it on all platforms. Public domains like
`api.z.ai` resolve through the system DNS resolver normally.

## Differences from the mock demo (07-ai-gateway)

- **Real LLM backends** instead of OpenAI-compatible mock servers
- **Provider path override** for z.ai's non-standard endpoint (the mock
  demo did not need this since mocks use the standard
  `/v1/chat/completions` path)
- **No semantic cache** — the mock demo used the mock's deterministic
  embeddings endpoint; real LLMs can be wired by pointing
  `ai.semantic_cache.embedding_url` at Ollama's `/v1/embeddings`
  endpoint (requires an embeddings model like `ollama pull nomic-embed-text`)
- **No A2A / MCP** — those features rely on mock-specific infrastructure
- **Canary verification via metrics** — with real LLMs, the response
  content does not echo the provider model name, so the canary split is
  verified via `/metrics` rather than response content
