# Category 10: TLS & Transport

Demonstrates the dwara gateway's TLS and transport-layer capabilities:
TLS termination, multi-SNI certificate selection, SNI passthrough
(documented), HTTP/2 over TLS, PROXY protocol (documented), native
gRPC proxying, HTTP/3 (QUIC) ingress, L4 TCP proxying, post-quantum
TLS, ACME (documented), and FIPS mode (documented).

| Multi-SNI cert selection | Tested | `test-02-multi-sni.sh` |
| SNI passthrough | Documented (limitation) | `test-03-sni-passthrough.sh` |
| PROXY protocol | Documented (opt-in) | `test-04-proxy-protocol.sh` |

## Architecture

```
                    +-------------------+
  client ---> :8080 | edge-http         | plaintext HTTP (h1 + h2c; grpcurl -plaintext)
            \
             \---> :8443 | edge-https         | TLS terminate (multi-SNI + mTLS, pq: true,
             \           |                    | Alt-Svc advertisement, acme block)
              \
               \-> :8444 | edge-passthrough  | TLS SNI passthrough (inert*)
                \
                 \-> :8445 | edge-h3          | HTTP/3 over QUIC (UDP)
                  \
                   \-> :8446 | edge-l4-tcp     | L4 TCP byte-splice proxy
                    \
                     -> :2019 | admin             | mTLS-only admin API

  * passthrough is configured but inert: the echo upstream is HTTP only,
    so a live TLS handshake through :8444 cannot complete. See below.
```

Upstreams (on the shared docker network):

- `echo`   (dwara-demo/echo)   on :8080 — reflects the request as JSON (HTTP only)
- `static` (dwara-demo/static) on :80   — serves demo HTML + JSON files
- `grpc`   (dwara-demo/grpc)   on :8080 plaintext and :8443 TLS+h2 —
  the `dwdemo.DemoService` (SayHello / ToUpper / Count) with
  reflection + health; published to the host on 19010/19012

## Prerequisites

- Docker + Docker Compose
- The prebuilt images:
  - `dwara:demo`            (the gateway; built from `Dockerfile.scratch`)
  - `dwara-demo/echo`       (echo upstream)
  - `dwara-demo/static`     (static upstream)
  - `dwara-demo/grpc`       (gRPC upstream; build it with
    `docker compose -f demos/_shared/docker-compose.yml build grpc`)
  - `dwara-demo/h3-client`  (optional; one-time:
    `docker compose --profile tools build h3-client`)
- The shared certs at `../_shared/certs/`:
  - `server.crt` / `server.key` — self-signed, CN=localhost,
    SAN `DNS:localhost,IP:127.0.0.1`
  - `client-ca.crt` — CA for client certificates (mTLS)
  - `client.crt` / `client.key` — a client cert for the admin API
- The gRPC upstream cert pair at `./grpc-certs/` (generated by
  `./gen-grpc-certs.sh`, CN=grpc, SAN `DNS:grpc,DNS:localhost,
  IP:127.0.0.1`; committed with the demo). The gateway trusts it via
  `trusted_ca_file`.

If `dwara:demo` is not tagged, `docker compose up` builds it from the
repo root via the `build:` fallback in `docker-compose.yml`.

## Expected results

- `test-01-tls-terminate.sh` — `curl --cacert ... https://localhost:8443/healthz`
  returns `200` with body `ok`.
- `test-02-multi-sni.sh` — `curl --resolve api.example.com:8443:127.0.0.1 ...`
  returns `200` (SNI=api.example.com selects the matching cert entry).
- `test-03-sni-passthrough.sh` — skips the live test and documents the
  HTTPS-upstream requirement.
- `test-04-proxy-protocol.sh` — verifies the plaintext HTTP listener
  works; documents that PROXY protocol needs an L4 LB in front.
- `test-05-http2.sh` — `curl --http2 ... https://localhost:8443/healthz`
  returns `200` and ALPN negotiates HTTP/2 (`http_version=2`).
- `test-06-grpc-proxying.sh` — `grpcurl` calls
  `dwdemo.DemoService/SayHello` / `ToUpper` / `Count` through the
  gateway (plaintext entry `:8080`, TLS entry `:8443`) and sees the
  greeting (`hello, demo!`), the uppercased text, and the complete
  server-streaming countdown (trailers survive the proxy hop).
- `test-07-http3.sh` — the `listening_h3` startup log and the
  host-side UDP `:8445` listener prove the QUIC listener bound;
  `edge-https` advertises `alt-svc: h3=":8445"` (protocol upgrade
  discovery); and, once `dwara-demo/h3-client` is built
  (`docker compose --profile tools build h3-client`), a live verified
  HTTP/3 GET over QUIC returns `200`.
- `test-08-l4-proxying.sh` — a raw TCP connection to `:8446` (python3
  stdlib socket) is spliced to the echo upstream and the HTTP response
  flows back; UDP L4 proxying is documented as stubbed.
- `test-09-pq-tls.sh` — with `tls.pq: true` configured, a normal
  `curl --cacert` handshake still succeeds (classical fallback), ALPN
  still negotiates h2, and the trust model is unchanged.
- `test-10-acme.sh` — the `tls.acme` block validates and coexists
  with the manual certificate (which still serves); live issuance is
  documented as runtime-stubbed.
- `test-11-fips.sh` — the OSS build serves TLS normally and omits the
  `fips` attestation from `/healthz`; enforcement itself is
  ent-gated and documented.

## Notes on the HTTPS tests

All HTTPS curls use `--cacert ../_shared/certs/server.crt` because the
server certificate is self-signed. The cert is valid for `localhost` and
`127.0.0.1` only.

The multi-SNI test (`test-02-multi-sni.sh`) sends SNI=`api.example.com`,
which is **not** in the cert's SAN. curl's hostname verification would
therefore fail, so that test adds `-k` to skip hostname verification —
the goal is to verify SNI-based *cert selection*, not hostname matching.
With a real cert that carried `api.example.com` in its SAN, `--cacert`
alone would suffice.

## SNI passthrough (documented limitation)

The `edge-passthrough` listener (`:8444`) is configured with
`tls.mode: passthrough` and an `sni_routes` entry mapping
`api.example.com` to `echo-upstream`. In passthrough mode the gateway
peeks the TLS ClientHello SNI and splices the raw TLS stream
byte-for-byte to the matched upstream — it does **not** terminate TLS,
so the upstream must speak TLS itself.

The `dwara-demo/echo` upstream is HTTP only (plaintext on :8080), so a
live client TLS handshake through `:8444` cannot complete. The listener
is included to demonstrate the `sni_routes` config shape; the live test
is skipped. To exercise passthrough end to end, point an `sni_route` at
an HTTPS upstream (e.g. an nginx container with TLS enabled).

## Native gRPC proxying (test-06)

gRPC is plain HTTP/2 traffic: RPC paths (`/dwdemo.DemoService/SayHello`)
match routes like any path prefix, and trailers (which carry
`grpc-status`) pass through the proxy hop untouched. Two things are
specific to the upstream hop:

- **The gateway's `protocol: http2` upstream transport is TLS with h2
  ALPN** — the gateway does not offer h2c prior-knowledge toward
  upstreams (`http1` is the plaintext choice, `https`/`http2` negotiate
  TLS; see `crates/dwara-core/src/dataplane/upstream.rs`). A native
  gRPC server must therefore LISTEN WITH TLS for the gateway to dial
  it. The demo gRPC image serves both: plaintext `:8080` (direct
  `grpcurl -plaintext` checks, published on host `19010`) and TLS+h2
  `:8443` (what the gateway dials, published on `19012`).
- **The upstream certificate must be valid for the endpoint hostname
  the gateway dials** (`grpc`, the docker service name) and trusted
  via `trusted_ca_file`. That is why the demo generates its own pair
  (`gen-grpc-certs.sh`, SAN `DNS:grpc,DNS:localhost,IP:127.0.0.1`)
  instead of reusing the quickstart `localhost` cert.

Clients enter on the shared listeners: plaintext `:8080` with
`grpcurl -plaintext` (the client's h2c prior-knowledge hop ends at the
gateway; the gateway's own hop to the upstream is TLS+h2 regardless) or
TLS `:8443` with `grpcurl -cacert` (h2 via ALPN).

## HTTP/3 (test-07)

The `edge-h3` listener (`:8445/udp`) is **live in the default demo
build**: quinn + h3 are compiled into `dwara-bin` unconditionally, the
gateway binds a UDP socket and runs a QUIC accept loop, and the
`listening_h3` startup log records the bind. `edge-https` advertises
the QUIC port via `alt_svc: 'h3=":8445"; ma=86400'`, the standard
protocol-upgrade discovery mechanism — HTTP/1.1 and HTTP/2 clients see
the `Alt-Svc` response header and may upgrade on their next connection.

Sending a real h3 request needs an HTTP/3-capable client: **macOS's
bundled curl has no HTTP/3 support**, and neither does the stock
`curlimages/curl` image. The demo therefore carries a minimal aioquic
client (`h3-client/`, built as `dwara-demo/h3-client` on demand):

```sh
# one-time: build the h3 client
docker compose --profile tools build h3-client

# verified HTTP/3 GET (dials the gateway inside the docker network;
# --server-name keeps certificate verification against the demo
# cert's localhost SAN):
docker run --rm --network 10-tls-transport_tls-net \
  -v "$PWD/../_shared/certs:/certs:ro" \
  dwara-demo/h3-client --cafile /certs/server.crt --server-name localhost \
  https://dwara:8445/healthz
```

(The test script runs this for you.) Note the docker-network dial:
**Docker Desktop does not reliably forward QUIC through published UDP
ports**, so the client connects to the gateway's network-internal
address rather than the published `:8445`. Any modern browser also
works — it upgrades automatically via the advertised `Alt-Svc`. The h3
listener requires TLS (QUIC is always encrypted) and serves terminate
mode only.

## L4 TCP/UDP proxying (test-08)

The `edge-l4-tcp` listener (`:8446`) proxies raw TCP: accepted
connections are spliced byte-for-byte to the `l4.upstream`'s endpoint
(picked through that upstream's load balancer), with an optional
`idle_timeout_s` closing idle splices. No HTTP pipeline runs — no
routing, transforms, auth, or request-level analytics — which is the
point: non-HTTP protocols (databases, SMTP, custom binaries) get
load-balanced byte transport. The live test speaks minimal HTTP over
the raw socket only because the echo upstream happens to speak HTTP.

The **UDP half is stubbed**: `protocol: udp` listeners are accepted by
the config schema but the dispatcher returns `Unimplemented` and the
listener does not bind (`udp_listener_skipped` log; UDP session/NAT
semantics are a follow-up). TCP `l4.sni_routing: true` reuses the SNI
extraction from TLS passthrough and carries test-03's HTTPS-upstream
requirement.

## Post-quantum TLS (test-09)

`tls.pq: true` on the `edge-https` terminate listener opts into the
hybrid X25519+ML-KEM key-exchange PREFERENCE: the hybrid group is
prepended to the kx group list with the classical X25519 kept as
fallback, so non-PQ clients keep working (asserted live by the test's
plain `curl --cacert` handshake). The flag is validated (rejected on
passthrough listeners; rejected in FIPS builds since ML-KEM is not on
the approved list) and metric-ready
(`dwara_tls_pq_handshakes_total{result}`).

**Status:** the actual kx-group installation
(`security::pq::install_pq_kx_group`) is a documented no-op in the
pinned rustls version — the experimental rustls hybrid-kx API is not
stable yet — so handshakes run with the classical group list today.
The per-upstream form (`upstreams[].pq: true`, TLS protocols only) is
the same mechanism on the gateway-to-upstream hop.

## ACME / Let's Encrypt (test-10, documented limitation)

The `edge-https` listener carries a `tls.acme` block (SEC-02):
`domains`, `contact`, `challenge: tls-alpn01` (kebab-case enum value),
`staging: true`, `state_dir`. The schema is fully accepted and
validated — but the ACME **client** is runtime-stubbed: no account
registration, challenge completion, issuance, or renewal runs in this
build. Because ACME manages only the fallback certificates, the manual
`cert_file`/`key_file` pair keeps serving; the test asserts exactly
that coexistence.

A real deployment additionally needs: a publicly resolvable domain,
port 443 directly reachable by the CA's validation servers (the
`tls-alpn01` challenge is answered during the TLS handshake; no
separate HTTP listener is required), and `staging: false` plus a
contact email for production issuance. Until the client lands, use an
external ACME tool (certbot, lego, cert-manager) and point the
gateway's cert paths at the issued files.

## FIPS mode (test-11, documented limitation)

FIPS 140-3 enforcement is a **build-time property of the Enterprise
edition** (`cargo build -p dwara-bin --features ent`, or
`Dockerfile.ent`): approved-only cipher suites, DRBG health checks,
and a startup self-test that refuses to boot on failure. There is no
YAML field for FIPS — nothing to toggle at runtime — and `pq: true` is
rejected at validation in a FIPS build (the two features are mutually
exclusive until ML-KEM reaches the validated list).

The OSS demo image runs `FipsMode::Disabled`: no cipher restriction,
no self-test, and `/healthz` omits the `fips` attestation object
(the field only appears when the mode is compiled in). The test pins
that OSS behavior; see `demos/11-enterprise/` and
`quickstart/enterprise/` for the ent-gated build path.

## Features that require special builds (recap)

- **FIPS mode** — `ent` cargo feature (Enterprise); the only genuinely
  feature-gated item in this demo.
- **HTTP/3** — compiled into the default build (live); only the
  *client* side needs special tooling (macOS curl lacks HTTP/3).
- **Post-quantum TLS** — config/validation/metrics are wired; the kx
  group itself is inert pending the stable rustls PQ API.
- **ACME** — config-accepted, runtime-stubbed; external ACME clients
  in the meantime.

See the repo-root `config-reference.json` and the OSS quickstart
(`quickstart/oss/dwara.yaml`) for the full schema and feature flags.

## Admin API (mTLS)

The admin API binds `:2019` with TLS and requires a client certificate
chained to `client-ca.crt`. Query it with the client cert:

```sh
curl -s --cacert ../_shared/certs/server.crt \
  --cert ../_shared/certs/client.crt \
  --key  ../_shared/certs/client.key \
  https://localhost:2019/health
```
